# Design & Architecture Review — Interpreter (.NET IL Interpreter / Dump-Time Evaluation)

## Executive summary

This is a documentation-first conceptual-design project for a reusable CIL (ECMA-335) interpreter whose distinguishing idea is executing IL *without* complete concrete state — propagating provenance-bearing "unknowns," havoc'd effects, and abstract-interpretation domains through one domain-parametric semantics engine, aimed first at post-mortem crash-dump evaluation and a "virtual" step-debugger. Its single most important strength is genuine design quality in the load-bearing places: the domain-parametric spine (`IValueDomain`/`IMemoryModel`/`ICallModel`), a strictly acyclic downward-only dependency graph with the execution core provably isolated from ClrMD/SRM/ILSpy, and a real end-to-end vertical seam (spawn target → write a real process dump → load via ClrMD → resolve metadata → single-step the VM) that proves the hardest integration works. Its single most important risk is a near-total imbalance between ambition and reality: roughly 80,000 words of design across 56 documents specify seven-plus multi-year subsystems, while the executing engine implements exactly one opcode (`ret`), 34 of 42 projects are empty shells, there is one test, and no CI enforces anything. The design surface has run far ahead of a finishable core, and the plan contains no effort, capacity, or sizing signal that would pull it back. **Overall verdict: promising design instincts trapped inside an over-scoped, under-validated program — fundamentally sound to build on, but only after a ruthless narrowing to one vertical slice.** Confidence: **high** (most load-bearing claims were independently verified against the repo).

## What the project is (grounded snapshot)

- **Documentation:** ~79,935 words across 56 Markdown files; ~20 proposal docs under `docs/proposals/architecture/` alone.
- **Solution:** 42 projects under `src/` (44 in `Interpreter.sln` including `TestTarget` + `IntegrationTests`).
- **Implemented vs empty:** only **8** src projects contain any C#; **34 are project-file-only stubs** (all Domains, Memory, Models, Symbols, Decompiler, DebugMaps, Analysis/IR/Tracing, and all four Products).
- **Real code:** ~1,633 lines of C#; ~66% is pure interface/enum/record/DTO contracts (~85 public types); executable logic lives in **5 files**. Only `IlMachine` has behavior, and it interprets exactly **one opcode** (`ret`, `0x2A`), faulting on everything else.
- **Tests:** **one** `[Fact]` (a real dump-loading integration test) plus a one-method `TestTarget`. Zero unit tests. No `.github/workflows`, no CI of any kind.

The doc-first posture is explicit and legitimate for a concept-phase repo. The problem is not that docs lead code — it is the *magnitude* of the lead and that the two top-level orientation docs (`README.md`, `prototype-solution-structure-proposal.md`) actively deny that any code/types exist, which is false in the same commit.

## Strengths (what genuinely works)

- **The central abstraction is the right one.** The domain-parametric spine (`IValueDomain<TValue>` + `IMemoryModel<TValue,TMem>` + `ICallModel`) is the correct way to reuse one semantics engine across concrete/hybrid/abstract modes and avoids the classic "built a concrete interpreter, now rewrite for analysis" trap.
- **Dependency direction is sound and machine-verifiable.** Every `ProjectReference` edge points downward, the graph is acyclic (Kahn toposort passes over all edges), and `Interpreter.Core.Execution` references only `Interpreter.Core.Abstractions` — no backend leakage into the VM. Concrete backends (SRM, ClrMD) are correctly isolated at the leaves.
- **The one real test is a genuine end-to-end seam, not a mock.** It writes a real full process dump via `DiagnosticsClient.WriteDump`, loads it with ClrMD, matches MVID, reads IL, and single-steps the VM. This is the right shape for a first bounded milestone and proves the hardest integration.
- **Safety/honesty posture is disciplined and differentiating.** Read-only dump, provenance-bearing unknowns, "prefer Unavailable over guessing," fail-closed to typed-unknown/`UnsupportedLayout`, no silent fallback to concrete guesses — all well-matched to the trust problem of dump evaluation.
- **The "lift the semantics, not the machinery" pattern is applied consistently** (intercept builder/awaiter and DLR call-site calls as intrinsics rather than interpreting TPL/DLR internals) and is the correct layering choice.
- **Docs are grounded in checkable primary sources** (coreclr `shared-generics.md`, ILSpy `CreateSequencePoints`/`DynamicCallSiteTransform`, ClrMD source, Portable PDB spec) rather than marketing, and `integration-test-plan.md` is an exemplary altitude-appropriate design that matches reality.

## Findings by theme

### Scope

**Aggregate scope is a union of ~7 team-year subsystems with no capacity-based forcing function.** *(High)* — 20 architecture docs specify, in depth, a deterministic IL interpreter, a CFG/fixpoint abstract interpreter, a virtual step-debugger with undo/branch-forking, async/Task virtualization, dynamic/DLR dispatch, generic-context reconstruction, and BCL semantic modeling — each historically comparable to a multi-year effort. The implemented engine supports one opcode. *Calibration:* the plan does contain scope-control mechanisms (milestone exit criteria, a scope-expansion risk item, technical decision gates), but none are anchored to any effort estimate, team size, or date, so nothing ties total scope to what a small effort can finish. **Why it matters:** "realistically sized" is literally unanswerable from the plan, and the honest reading of the declared goal as a whole is "not achievable as stated." **Recommendation:** pick ONE product surface (dump-time read-only expression evaluation) as the funded goal; relabel the other six subsystems and all non-dump product surfaces as "research backlog / not committed"; add a one-line scope-lock statement to `README` and `future-work-planning`.

**"One engine, all modes / multi-application platform" is asserted, not demonstrated — and partly refuted by its own docs.** *(High)* — `other-potential-applications.md` itself concedes the concrete no-JIT runtime mode needs a fully concrete domain, a real heap, a host ABI, verification, and performance engineering (its "biggest delta") — a different system from the safety-first unknown-propagating evaluator. The reuse claim is exactly the part with zero implemented evidence (all `Domain.*`, `Memory.*`, `Models.*`, `Product.*` empty). *(Verified detail: the empty `Product.*` projects declare dependency fans up to 15 references, not 18.)* **Why it matters:** presenting six speculative surfaces alongside a one-opcode prototype reads as strategic diffusion and inflates perceived scope. **Recommendation:** demote the multi-application material to an explicitly "speculative / not on the roadmap" appendix; do not re-assert multi-mode reuse until at least two domains (Concrete + CN-T) run the same opcode set through the same engine.

**The MVP has one real internal tension worth resolving (Span vs. `ldind`).** *(Medium — downgraded)* — `mvp-abstract-domain §12` markets Span/byref element reads as an MVP capability, while `opcode-support-matrix §4` places the `ldind.*/stind.*` opcodes they need at Tier C/D (post-MVP). *Calibration:* the earlier framing that the MVP is broadly "internally contradictory" and "excludes its own headline scenario" is **overstated** — deferring loop-capable LINQ to later phases is coherent phasing; a BCL model "emitting exceptional state" is compatible with EH opcodes being blocked; skipping budget tracking is consistent with an MVP that excludes loops; and both docs hedge the Span/`ldind` point. **Recommendation:** resolve the one genuine tension by defining the MVP as a self-consistent closed opcode set where every listed opcode's dependencies are also in the set.

### Architecture

**81% of projects are empty stubs — decomposition precedes any validated need.** *(High — confirmed)* — 42 csproj, 8 with code, 34 empty; the entire Domain/Memory/Models/Products/Symbols/Decompiler layering is unexercised by any code. "Start granular, merge later" is easy to state and rarely executed once 42 projects accrete git history, references, and CI wiring. **Why it matters:** the elaborate multi-layer structure is validated only by "does it compile," not by behavior. **Recommendation:** collapse toward the ~5 packages `architecture-overview §7` itself proposes until more than the ret-only seam exists; re-split a package only when it gains an implementation whose boundary a test exercises; keep the 42-name catalog as a documented target, not 34 compiled empty assemblies.

**One genuine interface-stability gap: `IValueDomain` cannot express its own lattice laws.** *(High for the gap; the rest downgraded)* — `IValueDomain` (21 members) exposes `Join`/`Widen` but no `leq`/`meet`, so the partial order the soundness spec mandates, and the `next ≤ widen` covering check, cannot be evaluated at the interface. *Calibration:* the companion claims were **overstated** — the `IResolutionServices` (Core) vs `IMetadataModule` (Metadata) overlap is a deliberate VM-facing-vs-per-module split with the delegation direction explicitly documented and shown via a `MetadataResolutionServices` adapter; and the three module-identity types (`ModuleHandle`/`ModuleId`/`RuntimeModuleId`) are an intentional opaque-handle-per-layer design with explicit mapping seams (`IRuntimeMetadataBridge.TryMapModule`, `IMetadataModule.Id` + `.ModuleHandle`, `IMetadataUniverse.TryGetModule`). **Recommendation:** add `BooleanLessThanOrEqual` (and optionally `Meet`) to `IValueDomain` so laws are checkable — treat this as blocking for the M0 "contracts" milestone. Leave the resolution/identity design as-is but add one canonical identity-mapping note for readers.

**The "clean" layer map is already contradicted by a reactive build-fix edge, and Products wire large fans into empty leaves.** *(Medium)* — `Metadata.Abstractions → Core.Abstractions` was added to make the solution compile, meaning `Core.Abstractions` is the true shared foundation, not a co-equal sibling as the diagram shows; and `Product.DumpDebugging` declares 15 references into projects that are all empty. **Recommendation:** redraw the layer map to show `Core.Abstractions` as the foundation (or extract a real `Shared.Abstractions`); defer the `Product.*` composition roots until at least one non-trivial leaf they compose has behavior.

### Technical feasibility

**Async/Task virtualization presupposes a near-complete IL interpreter plus EH that do not exist.** *(High — confirmed)* — Running `MoveNext` at all requires executing real IL (struct builders/awaiters, `ldflda`, generics, boxing) and the outer `try/catch` every compiler-generated `MoveNext` wraps user code in, yet the proposal intercepts only builder/awaiter calls and leaves "the rest" to "interpret IL normally." The engine has one opcode, no locals, no operand-stack semantics, no EH state. **Why it matters:** the gap between "intercept the builder" and "execute a `MoveNext`" is an entire interpreter, currently labeled a refinement. **Recommendation:** sequence a full IL interpreter and a real EH subsystem as explicit prerequisites *before* async, and make `virtual-tasks` depend on them in the roadmap.

**Exact `__Canon` de-canonicalization via dictionary decoding is infeasible as scoped — but the primary path is feasible.** *(High → scoped down)* — Reading `InstantiatedMethodDesc::m_pPerInstInfo` slots is DAC-level, version-pinned private-struct work with no public ClrMD API and no versioning strategy in the proposal. *Calibration:* this is only ONE ranked source. The proposal's **primary** anchor is the this-object `MethodTable` (reified generics), which ClrMD exposes publicly and which yields exact type arguments for instance methods and async/iterator `MoveNext` frames. Dictionary decoding is strictly needed only for **static** shared-generic code and method-level (`!!j`) args. **Why it matters:** the headline capability does not uniformly "degrade to unknown for optimized production dumps" — only that narrower slice does. **Recommendation:** reframe the exact-dictionary path as an explicit research spike gated on a version-pinned introspection service with per-CLR offset tables; set the honest baseline to `MethodTable`-anchored recovery plus typed-unknown fallback.

**Exception handling is a large subsystem sitting under async/dynamic/Step-Out — but the models don't strictly require full EH.** *(Medium — downgraded from High)* — IL EH (protected regions, `leave`/`endfinally`/filters, cross-frame unwinding, Step-Out through `finally`) is a major subsystem placed at Tier C while BCL models reference exceptional states. *Calibration:* the "MVP cannot realize its own models" framing is **overstated** — the docs already surface this as explicit open questions (opcode-matrix Q1, state-and-domain Q1), and domain-level "emit exceptional state" (terminate/taint/`ExceptionStop` a path) is separable from, and realizable without, full handler-transfer EH. What MVP genuinely defers is routing exceptions into interpreted user `try/catch` and Step-Out unwinding. **Recommendation:** promote EH to a first-class milestone with its own design doc; explicitly decide stop-on-throw (MVP) vs. handler transfer (later) rather than leaving three subsystems silently dependent on it.

**Abstract-interpretation soundness: one real interface omission, two areas the docs already flag.** *(Medium — downgraded from High)* — *Calibration:* of the three originally-claimed defects, only the missing `leq`/`meet` on `IValueDomain` is solidly grounded (covered above). The "widen=join diverges on Range" concern is hypothetical about an **optional, unimplemented empty stub** for which no widening is specified, and the design *does* state a back-edge widening/termination obligation; the "fresh-unknown-per-iteration breaks fixpoints" concern is explicitly anticipated in `il-interpreter-framework §6.2` ("avoid 'new unknown each iteration' explosions by canonicalizing"). **Recommendation:** when the Range/interval domain is actually implemented, specify a concrete widening operator with an ascending-chain-stabilization obligation; document the unknown-canonicalization rule at loop heads. Not urgent while those projects are empty.

**Deterministic execution over a dump is feasible for the narrow read path, but headline scenarios are undercut by dump reality, and "undo is basically free" overstates the design.** *(Medium)* — Release/optimized dumps routinely omit locals, args, and `this` — exactly the inputs the marquee "evaluate `request.User.Email`" scenarios need — and the current test reads IL from the on-disk module, not from dump memory. Separately, only the write-overlay is persistent; the ClrMD dump heap is non-versioned, and `TMem` is unconstrained, so branch-tree checkpointing, eviction/budget, and reversible allocation are the real (hand-waved) cost. **Recommendation:** quantify (even roughly) what fraction of target incidents supply the needed frame context; add a test that decodes IL from dump memory; constrain `TMem` with an explicit persistence contract and document undo cost honestly.

### Doc/code consistency

**`README.md` and `prototype-solution-structure-proposal.md` deny code/types that exist in the same commit.** *(High — confirmed)* — `README.md:25` says "no production code in this repo yet"; the structure doc says "no prototype types yet / only project files." In reality there are 42 csproj, ~1,633 LOC, ~85 public types, a working ret-only interpreter, and a passing integration test — and sibling docs (`prototype-interface-catalog`, `AGENTS.md`) contradict them. *(Correction: ~85 top-level public types, not "hundreds.")* **Recommendation:** reword both to state the true position ("a ret-only prototype slice exists: 8 projects, ~1.6k LOC, one integration test; 34/42 projects are empty scaffolding; one of ~200+ opcodes"); add a single-sourced "current implementation status" line referenced from all three docs.

**The project's own stop-reason standardization mandate is unmet across docs and code.** *(High — confirmed)* — `future-work-planning §2.1` mandates one taxonomy (`StepComplete, DecisionNeeded, ExceptionStop, BudgetStop, Completed`), but the implemented enum is `{Running, Completed, BudgetExceeded, Faulted}` (uses `BudgetExceeded`, not `BudgetStop`; missing the stepping reasons) and `virtual-tasks` uses a third, string-based set. Three vocabularies coexist and the reconciliation was not applied to the one place code exists. **Recommendation:** align `StopReason.cs` to the canonical names (or amend the mandate to the code's reality), and pick one home (`terminology-glossary.md`) that both code and docs cite.

**Package count/names and canonical-backend choice contradict across docs.** *(Medium)* — `architecture-overview §7` proposes 5 packages vs. the ~42 catalog and 42 real projects, with name drift; and `mvp-backend-decision-record` picks AsmResolver while `technical-stack-proposal` and the tail of `pe-pdb-reader-integration-proposal` still call SRM+ILSpy canonical (that doc contradicts itself top-to-bottom). The traceability map also marks zero-code features (`VS-01/02/03`, `X-05`) "Covered" against empty projects, conflating documented with validated. **Recommendation:** declare `module-architecture-proposal` the single source of truth for package layout; add an explicit retraction note reconciling AsmResolver vs SRM; split traceability status into "Designed" vs "Implemented/Validated."

### Plan

**No effort/timeline/capacity model; milestones are un-estimable monoliths.** *(High — partially calibrated)* — The plan is ordering-only, with no effort, dates, team size, or sizing anywhere (verified: no scheduling terms in the file). *Calibration:* each milestone *does* provide Deliverables + Exit criteria (a decomposition), so "single bullet list" is imprecise — but none of it is sized, so the roadmap cannot be scheduled or its realism assessed. **Recommendation:** decompose at least M0–M2 into estimable tasks with coarse sizing (S/M/L or ideal-days) and one explicit capacity assumption (e.g., "1 part-time maintainer"); even rough sizing exposes which milestones are unrealistic.

**Breadth-before-depth: four research subsystems are queued as active alignment work before the M1 MVP exists.** *(High — confirmed)* — `future-work-planning §2.1–2.4` label async, dynamic, semantic-modeling, and platform-expansion work as "immediate alignment updates ... now required," directly contradicting the plan's own `§1.2` ("foundations before broad feature surface") and `§5` mitigation ("architecture review before adding major surface area"). **Recommendation:** freeze `§2.1–2.4` expansion as "design-backlog, not active" until M1 passes its exit criteria; add an explicit WIP limit ("no new subsystem alignment docs until M1 exit").

**Sequencing: one real dependency tension (M3.5), not a three-way inversion.** *(Medium — downgraded from High)* — M3.5's exit criterion names "curated dump-backed scenarios" while the "Dump-aware hosting integration prototype" (M4) is sequenced after it. *Calibration:* the claim that M3.6 and M3.7 also require dump execution is **overstated** — M3.6 references dumps nowhere (async/dynamic fixtures only) and M3.7 only in design/contract deliverables. Because the metadata/memory-provider interfaces land in M0 and M4 is a hosting *integration* prototype, M3.x fixtures can plausibly run against curated snapshot data conforming to the M0 interfaces. **Recommendation:** clarify M3.5's exit criterion (run over curated fixtures conforming to M0 interfaces, not the M4 hosting integration) or pull a minimal dump-hosting slice forward.

**The risk register omits the project's dominant risks.** *(High — confirmed)* — `§5` lists four risks, all technical. Missing: single-maintainer bus factor (verified: 173 commits, one author) against a seven-surface vision; capacity-vs-ambition; LLM-authored/ungrounded docs (verified: pervasive second-person "your design" phrasing, and this review found numerous unreconciled taxonomies); and market/adoption. Worse, the one named meta-risk's mitigation ("architecture review before adding surface area") presumes a review body a solo project lacks — and `§2.1–2.4` already violates it. **Recommendation:** add explicit risks for bus factor (mitigation: cut to one surface), capacity vs. breadth, and doc-grounding; re-scope the "architecture review" mitigation to a self-enforceable WIP limit.

### Quality

**No CI whatsoever — the entire quality bar is unenforced, and build breakage already went uncaught.** *(High — confirmed)* — No `.github/workflows`, no CI config anywhere, for a 44-project solution; the HEAD commit is literally "Fix package versions and other errors" (evidence of prior silent breakage), against a strategy doc that specifies a full CI matrix and pipeline. **Why it matters:** this is the single largest, cheapest-to-fix quality risk. **Recommendation:** add a minimal GitHub Actions workflow now — `dotnet build` on the solution + `dotnet test` on the integration test, on push/PR. If the dump-writing test is environment-fragile, gate it behind a category and keep build + a fast unit test as the always-on signal.

**Determinism/replay — the release-blocking differentiator — has zero test coverage and no mechanism in code.** *(High — confirmed)* — The docs declare determinism "release-blocking" with a "0% replay-hash-mismatch" SLA, but no replay/hash/fingerprint mechanism exists in code and the one test runs its input once and compares no hash. **Why it matters:** the core claimed advantage of the whole system is completely unvalidated, even at the ret-only level where it would be nearly free. **Recommendation:** add a determinism smoke test now — run `StepOne` twice over the same input and assert byte-identical serialized outcome; extend as opcodes land.

**Test/perf specification is disproportionate to a one-opcode, one-test codebase.** *(Medium)* — A 4-dimension CI matrix over policies/modes/fixture-tiers that don't exist, and exact ms/percent SLAs with zero measured data, while the testing-strategy M0 exit ("unit tests for core interfaces exist") is unmet (zero unit test projects). **Recommendation:** mark the CI matrix and SLAs explicitly as "aspirational placeholders, not current commitments"; right-size near-term testing to unit tests for the implemented abstractions plus one differential harness.

### Governance

**Spec inflation / documentation-as-progress.** *(High — confirmed)* — ~80,000 words across 56 docs specify near-zero-implemented subsystems; `README` still says "no production code"; the doc index's forward plan is literally two more proposal files to write. The largest doc describes the smallest real slice. **Why it matters:** this is the classic pattern where taxonomies and registries substitute for validated code. **Recommendation:** adopt a "design just-ahead-of-code" rule — gate new deep-dive proposals behind their implementation milestone and mark speculative docs as such so volume is not mistaken for progress.

**The governance regime is mandated but its metadata/location rules are unimplemented (DoD only partially met).** *(Medium — downgraded from High)* — `docs/decisions/`, `docs/specs/`, and `docs/overview/` don't exist; the canonical glossary is in the wrong place; reviewed docs carry only a bare "Status: Draft." *Calibration:* the "self-failing / universally unmet DoD" framing is **overstated** — the DoD's index requirement is met (`docs/README.md` is a genuinely strong categorized index), docs are grouped by purpose, and one ADR-style record with owner/date metadata exists (`mvp-backend-decision-record.md`). For a solo design-phase repo the full regime is also disproportionately heavy. **Recommendation:** slim the governance proposal to what a solo repo will maintain (a status line + the README index), explicitly deferring owners/ADRs/specs until implementation begins — do not leave a mandate the repo visibly ignores.

## Recommendations (prioritized)

### P0 — do first (validate the architecture with the smallest end-to-end vertical slice)
The cheapest way to convert the biggest architectural bet from paper to evidence:
1. **Ship a concrete-domain arithmetic slice.** Implement ~4–6 opcodes (`ldc.i4`, `add`, `mul`, `ldloc`, `stloc`, `ret`) over a real `Concrete` `IValueDomain` + `IMemoryModel`, so `TValue`/`TMemory` actually carry values. This exercises the domain-parametric seam end-to-end for the first time.
2. **Add a differential oracle.** Compile 10–20 tiny C# methods with Roslyn, run them live on CoreCLR, run the same IL through the interpreter's concrete domain, assert equal results. This simultaneously proves the semantics engine, establishes the differential-test harness the docs describe, and gives the first perf-corpus datapoint.
3. **Add minimal CI** (`dotnet build` + `dotnet test`) and a **determinism smoke test** (run twice, compare serialized outcome).
4. **Add `leq`/`meet` to `IValueDomain`** so the lattice laws become checkable at the seam.
5. **Correct the orientation docs** to state the true implementation status.

**Stop doing:** writing new deep-dive proposals (semantic registry, async, dynamic, platform expansion); creating new empty projects; expanding the CI matrix / perf SLAs / governance regime; and treating traceability "Covered" as readiness.

### P1
- Pick and **scope-lock one product surface**; relabel the other six subsystems and non-dump surfaces as non-committed research.
- **Collapse the project count** toward the ~5 packages the overview itself proposes; re-split only on demonstrated need.
- **Reconcile the live contradictions**: stop-reason taxonomy (docs + code), package count/names, AsmResolver-vs-SRM canonical backend, `ExecState` deprecation.
- **Decide EH scope explicitly** (stop-on-throw for MVP vs. handler transfer later) and give EH its own milestone.
- **Add sizing** to M0–M2 tasks and one capacity assumption.

### P2
- Extend the integration test to decode IL from dump memory.
- Constrain `TMem` with a persistence contract; document undo cost honestly.
- Migrate cross-cutting canonical terms into the glossary (or downgrade its stated role).
- Quantify recoverable-context rates for optimized dumps.

## What to keep doing

- The **domain-parametric abstraction** and the **strict downward-only dependency discipline** — these are the load-bearing correct decisions; protect them.
- **Real end-to-end seams over mocks** (the dump-writing integration test) — make this the template for every milestone.
- **Grounding design in primary sources** and being **honest about hard parts** (generic dictionaries, ILSpy output stability, `MoveNext` prerequisites).
- **Phasing quality gates to maturity** (observe-only → soft → hard) and labeling SLAs provisional.
- The **`docs/README.md` index** and `integration-test-plan.md` — proof the team can write navigable, altitude-appropriate, reality-matched docs when scoped to what exists.

## Overall verdict & confidence

**Verdict:** The engineering instincts here are genuinely good — the central abstraction, the dependency hygiene, the safety posture, and the one real vertical seam are the marks of someone who understands the problem. But as a *program* it is over-scoped by roughly an order of magnitude relative to its capacity and validation: seven-plus multi-year subsystems specified in ~80k words, one opcode implemented, one test, no CI, and orientation docs that deny the code exists. **The declared goals as currently scoped are not plausibly achievable by a small effort.** A *narrowed* goal — deterministic, provenance-honest, read-only expression evaluation over a dump, proven by a concrete-domain vertical slice with a differential oracle — is both plausible and differentiating, and the existing architecture is a sound foundation for exactly that.

**Confidence: high.** Most load-bearing claims in this report were independently verified against the repository (project/file/LOC counts, the single opcode, the absent CI, the taxonomy divergences, the empty-project inventory, the single-author history). Where the underlying evaluations over-reached — MVP "self-contradiction," the "three-way" sequencing inversion, the abstract-interpretation "defects," the resolution/identity "instability," the `__Canon` blanket-infeasibility, and the governance "self-failing DoD" — I have softened or scoped them accordingly, and those calibrations are reflected in the findings above.

**What would change my assessment:** a working concrete-domain slice with a passing differential oracle in CI (would raise technical-feasibility confidence and architecture score materially); a scope-lock statement plus sizing (would move plan realism); or, conversely, continued expansion of design surface with no new executable behavior (would confirm the documentation-as-progress risk and lower the verdict toward "stalled concept").

## Appendix — Review methodology

This review was produced by a multi-agent process and then reconciled against the repository:

1. **Deep read (7 parallel agents)** — every proposal, plan, governance doc, and the actual `src/`/`tests/` code was read into structured briefs (claims + file-grounded evidence + concerns).
2. **Cross-cutting evaluation (7 parallel agents)** — one per dimension in the scorecard, each scoring 1–5 with file-grounded findings.
3. **Adversarial verification (19 agents)** — every critical/high finding was handed to a skeptic instructed to *refute* it against the actual files.
